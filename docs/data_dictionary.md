# Data Dictionary

**Catalog:** `humanoid_robotics` · **Layers covered:** Silver, Gold · **Companion to:** [`business_rules.md`](business_rules.md) (business definitions and enforcement rules — this document is the structural reference: every table, every column, every allowed value).

This document is generated to match the deployed schema exactly. The Gold section mirrors `scripts/gold/sql/comments.sql` (the `COMMENT ON` / `ALTER COLUMN ... COMMENT` DDL applied to the warehouse) — if the two ever disagree, `comments.sql` is the source of truth and this file is stale. The Silver section documents the intermediate tables that Gold is built from; it is lighter-weight (purpose + key columns) since those tables are implementation detail, not the query surface for BI/Genie.

## Gold layer

### `gold.dim_date`
Calendar dimension, one row per day from 2020-01-01 to 2030-12-31. Used to slice `fct_events` by year/quarter/month.

| Column | Type | Description |
|---|---|---|
| `date` | DATE | **Primary key.** Joins to `fct_events.event_date`. |
| `year` | INT | Calendar year extracted from `date`. |
| `quarter` | INT | Calendar quarter (1–4) extracted from `date`. |
| `month` | INT | Calendar month (1–12) extracted from `date`. |
| `year_month` | STRING | Year and month formatted as `yyyy-MM`, e.g. `2026-10`. |
| `year_quarter` | STRING | Year and quarter formatted as `yyyy-Qn`, e.g. `2026-Q4`. |

### `gold.dim_source`
One row per source document (news article, press release, or filing) ingested into the pipeline, enriched with its AI-generated summary and event count.

| Column | Type | Description |
|---|---|---|
| `doc_id` | STRING | **Primary key.** Unique identifier of a source document. |
| `title` | STRING | Document title/headline, translated to English via `ai_translate` when the original language was `zh`. |
| `publisher` | STRING | Name of the publishing outlet or organization. |
| `source_type` | STRING | Type of source document. See [Enumerated values](#enumerated-values-reference). |
| `language` | STRING | Original language of the document before translation. See [Enumerated values](#enumerated-values-reference). |
| `publish_date` | DATE | Date the document was published. Used to resolve relative dates during AI extraction and as the fallback for `fct_events.event_date` when no explicit event date is stated. **This is an actual `DATE` value** — do not confuse with the boolean column of the same name on `fct_events` below. |
| `url` | STRING | Source URL of the document, when available. |
| `primary_company` | STRING | Company the document is primarily about, as identified in the ingestion manifest. |
| `summary_en` | STRING | 2–3 sentence English-language summary of the document, generated by the `ai_query` extraction step. |
| `event_count` | INT | Number of events the AI extraction step found in this document (0 if none, or if the document has not been processed yet). |

### `gold.dim_company`
One row per company referenced anywhere in the extracted event data (manufacturers, suppliers, investors, customers, partners). See [BR-CO](business_rules.md#5-companies-br-co) for how this table is curated.

| Column | Type | Description |
|---|---|---|
| `company_id` | STRING | **Primary key.** Stable surrogate key, no business meaning, never changed (BR-CO-03). |
| `company_name` | STRING | Standard English company name — the short name most commonly used in news. |
| `company_name_zh` | STRING | Company name in Chinese, when available. |
| `company_type` | STRING | What the company *is*. See [Enumerated values](#enumerated-values-reference). Independent of whether it's a research focus company (BR-CO-01). |
| `country` | STRING | Country where the company is headquartered. |
| `region` | STRING | Region where the company is headquartered. Distinct from `fct_events.region`, which is where a specific *event* took place, not where a company is based. |

### `gold.dim_technology`
Static lookup of the 6 technology areas used to tag events (sensors, compute & electronics, software & AI, actuators, battery & power, not specified). Not derived from source data — seeded directly in the build notebook.

| Column | Type | Description |
|---|---|---|
| `technology_id` | STRING | **Primary key.** Stable slug for a technology area, e.g. `sensors`, `compute_electronics`. |
| `technology_name` | STRING | Human-readable display name of the technology area. |
| `sort_order` | INT | Suggested display order for reporting/UI (1–6). |
| `description` | STRING | One-sentence definition of what this technology area covers. |

### `gold.fct_events`
**Fact table.** One row per de-duplicated humanoid-robotics industry event (funding, partnership, product launch, production plan, or policy announcement) extracted by AI from news/press-release text. **Grain: one event.** Event de-duplication is currently a placeholder 1:1 mapping — see `source_count` below and [BR-EVT-06](business_rules.md#32-event-rules) (status: Planned).

| Column | Type | Description |
|---|---|---|
| `event_id` | STRING | **Primary key.** Surrogate key for a de-duplicated event, derived from the `doc_id` and position of the extraction that produced the canonical record. |
| `event_type` | STRING | Category of the event. See [Enumerated values](#enumerated-values-reference). |
| `event_date` | DATE | Date the event occurred, as stated or inferred by the AI extraction model. Falls back to the source document's publish date when no explicit event date is stated in the text. **Foreign key** to `dim_date.date`. |
| `publish_date` | BOOLEAN | **Not a date, despite the name.** `true` when `event_date` above was inferred from the source document's publish date rather than an explicit date stated in the text (i.e. no explicit event date was found). This is **not** the document's publish date — see `dim_source.publish_date` for that. The name collision is a known issue, tracked for a future rename; see `fct_events.publish_date` comment in `comments.sql`, [BR-DATE-02](business_rules.md#4-dates-and-time-periods-br-date) and [BR-DATE-06](business_rules.md#4-dates-and-time-periods-br-date) (status: Proposed). |
| `amount` | DOUBLE | Monetary amount associated with the event (e.g. funding round size), denominated in `currency`. Null if no amount was stated or not applicable to this `event_type`. In native currency — **no FX conversion exists in this schema** (see [BR-AMT](business_rules.md#7-amounts-and-currency-br-amt)); always pair with `currency` before aggregating. |
| `currency` | STRING | ISO 4217 currency code for `amount`, e.g. `USD`, `CNY`. Null when `amount` is null. |
| `region` | STRING | Region where the event took place — not necessarily where the involved companies are headquartered. See [Enumerated values](#enumerated-values-reference). |
| `evidence_quote` | STRING | One sentence copied verbatim from the source article by the AI extraction model, as evidence supporting this event. |
| `primary_source_doc_id` | STRING | `doc_id` of the document used as the canonical/primary source for this event after de-duplication. **Foreign key** to `dim_source.doc_id`. See `bridge_event_source` for every document that reported this event. |
| `source_count` | INT | Number of source documents that reported this event, post-dedup. Currently always `1` because event de-duplication is a placeholder 1:1 mapping ([BR-EVT-06](business_rules.md#32-event-rules), status: Planned). |

### `gold.bridge_event_company`
Many-to-many link between `fct_events` and `dim_company`, carrying the company's role in each event. A company can appear in the same event with more than one role. **Composite primary key:** (`event_id`, `company_id`, `role`).

| Column | Type | Description |
|---|---|---|
| `event_id` | STRING | **Foreign key** to `fct_events.event_id`. |
| `company_id` | STRING | **Foreign key** to `dim_company.company_id`. |
| `role` | STRING | Role this company played in this specific event. See [Enumerated values](#enumerated-values-reference). **Known issue:** `target` and `issuer` are inconsistently assigned for funding recipients in prompt v1 — see [BR-ROLE-03](business_rules.md#6-eventcompany-roles-br-role). |

### `gold.bridge_event_technology`
Many-to-many link between `fct_events` and `dim_technology` — one event can relate to multiple technology areas. **Composite primary key:** (`event_id`, `technology_id`).

| Column | Type | Description |
|---|---|---|
| `event_id` | STRING | **Foreign key** to `fct_events.event_id`. |
| `technology_id` | STRING | **Foreign key** to `dim_technology.technology_id`. |

### `gold.bridge_event_source`
Many-to-many link between `fct_events` and `dim_source` — every document that reported a given event (not only the primary source), with a flag marking the primary one. **Composite primary key:** (`event_id`, `doc_id`).

| Column | Type | Description |
|---|---|---|
| `event_id` | STRING | **Foreign key** to `fct_events.event_id`. |
| `doc_id` | STRING | **Foreign key** to `dim_source.doc_id`. |
| `is_primary_source` | BOOLEAN | `true` when this `doc_id` is the canonical/primary source recorded on `fct_events.primary_source_doc_id` for this `event_id`. |

**Keys note:** all primary/foreign key constraints above are declared in SQL (`scripts/gold/99_gold_constraints.dbquery.ipynb`) via `ALTER TABLE ... ADD CONSTRAINT`. They are informational, not enforced at write time, but are visible in Catalog Explorer and used by Genie to understand how the tables relate.

## Silver layer

Intermediate tables between raw ingestion (Bronze) and the star schema (Gold). Documented at purpose + key-column level; see the corresponding notebook under `scripts/silver/` for full transformation logic.

### `silver.company`
Company master data. `UNION ALL` of two curated bronze seed tables (`bronze.company_seed`, `bronze.company_other`), trimmed and type-cast. Key columns: `company_id` (lowercased), `company_type` (lowercased, restricted to the fixed enum — see [Enumerated values](#enumerated-values-reference)), `founded_year` (INT), `is_listed` / `is_core` / `verified` (booleans, cast from `Y`/`N` seed values). This is the table `gold.dim_company` is built from.

### `silver.company_alias`
Alias → company name mapping (trimmed pass-through of `bronze.company_alias`), intended for matching spelling/script variants (e.g. Chinese names, full legal names) that don't match `silver.company.company_name` directly. Per [BR-CO-04](business_rules.md#5-companies-br-co), kept in the schema but not yet wired into the matching logic in `silver.event_companies` — matching currently relies only on exact `upper(trim())` equality against `company_name`.

### `silver.documents`
One row per source document after joining the ingestion manifest (`bronze.manifest_pilot`) to raw document text (`bronze.documents`) on `file_name`, translating non-English content via `ai_translate`, and casting `publish_date` to `DATE`. Key columns: `doc_id`, `title`, `publisher`, `source_type`, `language` (original language, before translation), `publish_date`, `primary_company`, `raw_text`, `char_count`, `url`. This is the table `gold.dim_source` is built from (joined to `document_summaries` for `summary_en`/`event_count`).

### `silver.documents_clean`
Output of rule-based text cleaning (`src_text_cleaning` module, `CLEANING_VERSION = "v2"`) applied line-by-line to `silver.documents.raw_text`, stripping boilerplate the upstream web-extraction step misses (e.g. "About the company" sections, media-contact blocks, recruiting footers). Key columns: `doc_id`, `clean_text` (truncated to `MAX_CHARS = 12,000` before being sent to any AI model), `raw_char_count`, `cleaned_char_count`, `removed_ratio`, `raw_line_count`, `removed_line_count`, `is_truncated`, `language`, `cleaning_version`, `cleaned_time`. `clean_text` is the input to both `ai_classify` (relevance) and `ai_query` (event extraction).

### `silver.documents_relevance`
One row per document, holding the output of `ai_classify(clean_text, ['about_humanoid_robots', 'not_about_humanoid_robots'])`. Key columns: `doc_id`, `relevance_label`, `is_relevant` (BOOLEAN), `classified_at`. Only documents with `is_relevant = true` proceed to event extraction (see [BR-SCOPE-03](business_rules.md#2-analysis-population-br-scope), status: To verify).

### `silver.documents_extractions`
**Append-only** log of every AI extraction call (`ai_query` against `databricks-gpt-oss-120b`) over `documents_clean`, one row per attempt. Key columns: `doc_id`, `prompt_version` (currently `v1`), `model_name`, `ai_raw_json` (the raw structured-JSON response), `ai_error` (non-null on a failed call), `extracted_at`. Never replaced or overwritten — a new prompt version adds new rows rather than mutating old ones (see [BR-AI-04](business_rules.md#10-ai-extraction-governance-br-ai)).

### `silver.v_extractions_parsed`
A view (not a table) that parses `documents_extractions.ai_raw_json` into a typed `STRUCT`/`ARRAY` using `from_json`, keeping only successful extractions (`ai_error IS NULL`) under the currently active `prompt_version`, and taking the latest attempt per `doc_id`. Feeds `document_summaries` and `events_extracted` below.

### `silver.document_summaries`
One row per document: `doc_id`, `summary_en` (AI-generated), `event_count` (`size()` of the parsed events array), `prompt_version`, `model_name`. Source of `gold.dim_source.summary_en` / `event_count`.

### `silver.events_extracted`
One row per **extracted** event (before de-duplication) — a document with 3 events in its AI output produces 3 rows here. Key columns: `doc_id`, `event_id` (format `<doc_id>_E<two-digit position>` — note: this is the *extracted* event id, not yet the de-duplicated `gold.fct_events.event_id`; see the naming clarification under [BR-EVT-05/07](business_rules.md#32-event-rules)), `event_type` (out-of-enum model output is coerced to `other`), `status`, `event_date`, `publish_date` (BOOLEAN — same "was the date imputed" flag as `gold.fct_events.publish_date`, defined here as `try_to_date(event_date) IS NULL`), `companies` (array of `{name, name_original, role}`), `technology_areas`, `components`, `application_sector`, `region`, `amount`, `currency`, `quantity`, `quantity_unit`, `evidence_quote`, `prompt_version`.

### `silver.event_companies`
One row per (extracted event, company mention), produced by exploding `events_extracted.companies` and matching each extracted name against `silver.company` via `upper(trim())` equality. Key columns: `event_id` (extracted), `doc_id`, `company_pos`, `company_name_raw`, `name_original`, `role` (normalized with `lower(trim())`), `company_id` (null if unmatched), `company_name_std`, `is_matched` (BOOLEAN). Unmatched rows (`is_matched = false`) are excluded from `gold.bridge_event_company` and instead reviewed via `datasets/review/07_company_candidates.csv` (see [BR-CO-05](business_rules.md#5-companies-br-co)).

### `silver.event_dedup_map`
Maps each **extracted** event to its de-duplicated **real-world** `event_id`. Key columns: `extracted_event_id`, `doc_id`, `event_type`, `event_date`, `publish_date`, `event_id`, `n_sources`. **Currently a placeholder**: `event_id = extracted_event_id` and `n_sources = 1` for every row — real de-duplication logic (same `event_type` + same company set + dates within 14 days, per [BR-EVT-06](business_rules.md#32-event-rules)) is Planned, not yet implemented. This is the single point that `gold.fct_events`, `bridge_event_company`, `bridge_event_technology`, and `bridge_event_source` all join through, so implementing real dedup here is sufficient to fix `source_count` and the one-event-per-document-mention problem across the whole Gold layer.

## Enumerated values reference

Fixed value lists used across Silver and Gold. These are the authoritative definitions — if a table/column comment and this section ever disagree, treat it as a bug to fix, not a judgment call. Full context and rule IDs are in [`business_rules.md`](business_rules.md).

### `event_type` (`fct_events`, `events_extracted`, `bridge_event_company` via join)
| Value | Definition |
|---|---|
| `funding` | Financing, investment, IPO, M&A |
| `partnership` | Collaboration, supply agreement, joint development, pilot deployment |
| `product_launch` | New product, new version, or new component release |
| `production_plan` | Mass-production plans, capacity, factories, delivery targets |
| `policy` | Government policy, standards, regulation |
| `other` | Cannot be assigned to any of the above; any out-of-enum model output is coerced here (see [BR-EVT-01](business_rules.md#32-event-rules)). Excluded from analysis by default ([BR-EVT-02](business_rules.md#32-event-rules)). |

### `role` (`bridge_event_company`, `event_companies`)
| Value | Definition |
|---|---|
| `target` | The company that receives the investment, is acquired, or is the subject of the transaction |
| `issuer` | The company issuing shares or making the announcement (e.g. IPO issuer, filing issuer) |
| `investor` | A company providing capital |
| `customer` | A company buying, ordering or deploying the product |
| `supplier` | A company supplying products, components or services |
| `partner` | A company in a collaboration without a clear buyer/seller relationship |

Known issue ([BR-ROLE-03](business_rules.md#6-eventcompany-roles-br-role)): in prompt v1, the funding recipient is labelled inconsistently as `target` or `issuer`. Until prompt v2 fixes this, treat the two as equivalent for funding.

### `technology_area` (`dim_technology`, `bridge_event_technology`)
| Value | Definition |
|---|---|
| `sensors` | Components that perceive the environment or the robot's own state (camera, radar, LiDAR, IMU, force/torque and position sensors) |
| `compute_electronics` | Processing hardware and control electronics (AI chips, SoCs, controllers, motor drivers) |
| `software_ai` | Software and AI models (perception, motion planning, control software, foundation models) |
| `actuators` | Components producing motion (motors, harmonic reducers, planetary roller screws, dexterous hands) |
| `battery_power` | Energy storage and power systems (battery packs, BMS, charging, power distribution) |
| `not_specified` | The event does not mention a specific technology area. Must not co-occur with another technology area on the same event ([BR-TECH-02](business_rules.md#9-technology-classification-br-tech)). |

### `company_type` (`dim_company`, `silver.company`)
| Value | Definition |
|---|---|
| `humanoid_maker` | Develops or manufactures humanoid robots |
| `tier1` | Automotive tier-1 supplier |
| `investor` | Investment firm / corporate venture arm whose main role is investing |
| `customer` | Company whose main relation to the industry is buying or deploying robots |
| `technology_partner` | Provides chips, software, AI models or other technology |
| `other` | None of the above |

Independent from `is_focus_company` (whether the company is a research target of this project) — see [BR-CO-01](business_rules.md#5-companies-br-co).

### `source_type` (`dim_source`, `silver.documents`)
`press_release`, `filing`, `news`, `policy`.

### `language` (`dim_source`, `silver.documents`)
`en`, `zh` — original language of the document before translation.
